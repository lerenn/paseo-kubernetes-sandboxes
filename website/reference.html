Reference

Settings

  • Image: needs a shell and your tools. Required.
  • CPU / memory: requests and limits of the main container.
  • Worktree volume: claim, mount path (same path in the pod), optional sub path. Required.
  • Idle timeout: minutes before an idle pod is deleted; 0 disables it.
  • Environment Secret: optional Secret exposed as environment variables.
  • Sidecars: named extra containers (image, command, env, resources, readiness probe, state volume, optional privileged flag), enabled by default or per workspace. Docker is a documented example, not a preset.
  • Pod overrides: runtimeClassName, tolerations, nodeSelector, priorityClassName, imagePullSecrets.
  • Context, namespace: where pods are created.

Sidecars

See Sidecars in the setup guide: fields, a docker example, requirements, and what is not tested. A privileged sidecar is weaker isolation.

Hooks

  • agent.open.before, terminal.create.before, command.run.before: return wrap for opted-in workspaces.
  • workspace.archive.after: deletes the workspace's pod.

Pod

Named sbx-<hash of workspace id>, labelled app.kubernetes.io/managed-by=paseo-kubernetes-sandboxes, with a shared process namespace and no service account token. The main container idles; work arrives through kubectl exec.

Launcher

kube-exec.sh --namespace NS --pod POD [--context C] [--container main]
  [--cwd DIR] [--env NAME]... [--state-dir /tmp/sbx] -- command [args...]

Forwarded variable values travel as kubectl exec arguments. Use the environment Secret for credentials.

Cluster admin tasks

The plugin runs as the cluster identity kubectl uses on the daemon host. Day to day it only creates and deletes pods in its sandbox namespace, runs exec and reads logs there, and (clone mode with a per-sandbox volume) creates and deletes its own claims. None of that is admin work. An admin does these once:

  • create the sandbox namespace;
  • apply the Role in config/plugin-rbac.yaml and bind it to the identity kubectl uses;
  • the cases below, when you use them.

Sharing the Paseo worktrees volume

Shared worktree mode mounts the daemon's worktrees folder and the main repository's .git into each pod. A PersistentVolumeClaim cannot be mounted from another namespace, so the volume must be mountable from the sandbox namespace, and it must support several writers (ReadWriteMany) unless all pods land on one node. Options for an admin:

  • Use the namespace that already holds the claim as the sandbox namespace (and bind the Role there).
  • Give the sandbox namespace its own claim on the same underlying volume: a static PersistentVolume with reclaim policy Retain (so deleting one claim does not delete the data) plus a PersistentVolumeClaim in the sandbox namespace bound to it. This works only if your storage provider supports a volume being used this way.
  • Use clone mode: no shared volume is needed, but Paseo's file tree, diffs and git status do not show what the agents did in the pod; results come back through git.

Whichever you choose, the mount paths, sub paths and file ownership (fsGroup / uid; see Run as user ID) in the plugin settings must match how the files sit on the volume and who owns them.

Docker in a sandbox (privileged sidecar)

Docker is not built in: it is a sidecar you define. A docker-in-docker sidecar typically needs privileged: true. A namespace whose Pod Security level is baseline or restricted rejects such pods, so an admin must provide a namespace that allows privileged pods (or an alternative runtime they trust). The workspace volumes are mounted into the sidecar at the same paths as in the main container, so bind-mount paths resolve.

Isolation. A privileged container is close to root on the node. The plugin gives resource and process isolation; it is not a security boundary, and a privileged sidecar weakens it further.

Not tested on a real cluster (see the setup guide): docker bind mounts of paths that come from subPath volume mounts; file ownership of files written by containers started through the sidecar; the docker:dind entrypoint in a shared process namespace; whether the 25-second launch timeout is too short for a cold image pull; eviction when the state volume or ephemeral storage limit is exceeded; whether a namespace that denies privileged pods gives a readable error; nested resource limits.
