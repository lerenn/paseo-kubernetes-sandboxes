Paseo + Kubernetes

Run a workspace in a pod.

Run a Paseo workspace's agents, terminals and commands in a Kubernetes pod. The workspace stays on your Paseo daemon; only the processes move.

Get startedView on GitHub

Opt in per workspace

Pick the workspaces that run in a pod. Everything else is unchanged. Each opted-in workspace gets its own pod, created on first use and removed when the workspace is archived or stays idle.

Storage modes

Each workspace uses one of two modes; a default applies to workspaces that do not choose.

  • Shared worktree: the pod mounts the workspace's worktree (and the repository's .git directory) from a PersistentVolumeClaim, at the same absolute paths as on the daemon. Files are shared with the daemon.
  • Pod-local clone: the pod clones the workspace's origin remote into its own storage (emptyDir or a PVC). Nothing is shared with the daemon's files, and the workspace needs an origin remote.
Storage modes are new and have not been tested against a real daemon and cluster.

No operator, no daemon in the pod

Paseo 0.17.5 lets a plugin return a launch wrap from hooks. This plugin returns a small launcher that runs the command with kubectl exec. The pod is a plain executor created directly with kubectl.

Early version. Resource and process isolation, not a security boundary: the pod limits CPU and memory and separates processes, and in shared-worktree mode it shares the worktree volume with the daemon. If the plugin is disabled, work silently runs locally. Not yet tested against a real daemon and cluster.
