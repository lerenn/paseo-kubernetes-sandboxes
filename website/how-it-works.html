How it works

Launch wraps

Before an agent, terminal or paseo.json setup/teardown command starts, Paseo asks plugin hooks for a wrap. For an opted-in workspace the plugin makes sure the pod exists and returns [kube-exec.sh, options, "--"]. Paseo runs the wrap followed by the original command; the launcher runs it in the pod and passes stdin, stdout and the exit code through.

Pod lifecycle

Pods are created on first use and deleted on workspace archive, idle timeout, or from the Pods tab. A sweep every minute removes idle pods; the first sweep after start also removes pods whose workspace no longer exists.

Stopping

On TERM, INT or HUP the launcher kills the remote process with a second kubectl exec. SIGKILL cannot be trapped: the remote process then lives until the pod is deleted.

Limits

  • Disabling the plugin makes opted-in workspaces run locally again, silently.
  • A wrapped shell has no Paseo shell integration, so paseo.json scripts do not report completion.
  • Resource and process isolation, not a security boundary. In shared-worktree mode the pod shares the worktree volume with the daemon.
  • Pod-local clone mode needs an origin remote, and changes stay in the pod until pushed (an emptyDir clone is lost when the pod is deleted).
  • Teardown commands use an existing pod and otherwise run locally; the archive/teardown order is unconfirmed.
  • Not tested: specific agents, port forwarding, file views, long idle connections.
